# GroundedOps: from 7 to 10

Branch experimental/v16.4-logic-and-latency, written 2026-09-27 from nine subsystem readers, five planner theses and the adversarial verdicts on 37 proposal clusters (33 kept with changes, 4 rejected, 0 unverified). Every claim carries a file:line or a document line. Where a planner and the verifier disagreed, section 8 says which side this plan takes and why. Effort figures are the verifier's, not the planners'.

## 1. Diagnosis

The bot is a 7 because it meets every Level-7 criterion for a B2B manuals bot and none of Level 8 in full. What it does: scoped hybrid retrieval with page-cited answers (src/main.py:2030-2080 _build_sources; README.md:227-241), a fail-closed grounding gate where NLI settles about 54% of turns, the LLM verifier about 36% and about 10% are refused (PENDING.md:217-222), a curated FAQ served before retrieval (22 of the 34 tuned cases never touch retrieval, PENDING.md:1002-1004), handoff, greeting, commercial and document-download intents answered in under a second (docs/stress-test-2026-09-25.md:73-79), and condense-rewrite follow-ups over the last two turns (src/text_utils.py:516-540). The numbers that define it: graded tuned suite 32/34 armed at repeats=1 (src/eval_baseline.json:2-3, pass_rate 0.941); blind set 1 now 30/34 but no longer blind, because it was read to make fixes (commit 8d9f5ca message: "Blind set 1, used for diagnosis: 24 -> 30"); blind set 2 25/34 on both v16.3 and HEAD in single runs (same message), of which about three are instrument false negatives (over-narrow keywords under exact substring matching at src/eval.py:187, and a friendly refusal scored as "answered" at src/eval.py:108-110); 53/59 live turns (docs/stress-test-2026-09-25.md); 142/160 routing checks with 18 label disagreements deliberately left as the engineer wrote them (PENDING.md:256-258); median 3.9s and p90 8.7s per turn measured by src/tests/run_live.py on an idle box (docs/stress-test-2026-09-25.md:57-58), against a contended-box log that reads p50 6.3s / p90 30.7s because 406 of its 503 timed rows are eval traffic from one day (K17 verdict). Run-to-run noise on a 34-case graded suite is +/-3 cases on identical code (PENDING.md:598-600), so no 1-3 case delta anywhere below counts as evidence unless it is a per-case 3-repeat outcome or a deterministic count. The customer-visible gaps: a fluent "No." served at grounding 0.001-0.002 whenever the manual never mentions the thing asked (Bluetooth x3, coins x3, SCS facial recognition x5 in src/logs.jsonl, all flagged=false because the LLM verifier at src/main.py:562-584 judges only SUPPORT and RELEVANCE); "and step 3?" re-retrieved as a fresh question (docs/stress-test-2026-09-25-transcripts-after.md:199-208); a two-product comparison scoped to one manual when a product is picked (src/main.py:2001-2002) and a spec-index comparison that finds 0 shared attributes for the NV9 pair because the two manuals' table captions differ only in letter case (K04 verdict); refused turns erased from memory so the next follow-up loses its referent (src/memory.py:46-59); the widget's handoff turn still contradicting itself because /widget/ask never forwards `role` (src/widget_api.py:510-552 vs src/widget/groundedops-widget.js:2116); no per-answer feedback anywhere; English only; no streaming and no real progress signal; and underneath all of it no way to tell customer traffic from harness traffic, because the log has no session, origin or outcome field (src/logger.py:70-94), while guest AI is off (src/policy.py:38) and the only public address is a quick tunnel that rotates on restart (serve.ps1:179; PENDING.md:736-748). Verifiable real-customer traffic is close to zero (src/widget_leads.json holds one developer test lead; conversations.db holds test-user-1 and preview-* only), so today every rating above 7 is a harness rating.

## 3. How to read the plan

Kinds: (a) switch on or wire up something already built; (b) verify something built but unverified; (c) build new; (d) measure only; (e) outside the code.

Noise floor. A graded 34-case run moves +/-3 cases on identical code (PENDING.md:598-600); the retrieval suite had 4/30 unstable cases at 3 repeats (PENDING.md:1384-1391); five live turns flipped across four runs at temperature 0 (docs/stress-test-2026-09-25.md:37-42; src/llm.py:346, 419, 463 send temperature 0 with no seed). So the detector for every upgrade is a deterministic check (unit test, count, per-case 3-repeat outcome); the graded suites (tuned 32/34, blind2, run_live 53/59, run_scenarios 142/160) are gates that must not fall below their re-armed stable baseline, never the evidence that something improved. After M4 re-arms the baseline at --repeats 3, "32/34 unchanged" is no longer a gate anywhere in this plan: the gate is the re-armed stable set N/N at --repeats 3, and every item below says so.

"Verifier's changes" under each item lists what the verifier struck or rewrote in the planners' proposal; the item is to be built as amended. Two repository rules this plan obeys: never tune against a blind set (PENDING.md:137-138, 1441); grep before building (three duplicates have already been written).

Uncommitted work by another session (src/ocr.py, src/tables.py, src/clarify.py, src/figures.py, complete_tables in src/retrieval_db.py, the phrase arm, the main.py:2725 clarify gate) is treated as landing; anything touching src/main.py is staged by hunk. "Landing" does not mean "verified": the phrase arm and complete_tables have no test (M14) and are not baked into the live index until 9.7's gates pass.
